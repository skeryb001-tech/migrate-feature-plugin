# Web 与客户端功能迁移

## 前置约束

用两个锚点裁决迁移：

1. **行为等价**：相同输入产生相同输出、状态转换、副作用、错误反馈和用户可感知结果。
2. **目标优先**：复用目标已有能力，遵循目标目录、分层、命名、请求/bridge、状态、UI 和测试规范。

源项目或源页面保持只读；保护目标工作区已有改动；同名文件不得直接覆盖。新增或变更依赖、SDK、plugin、数据库结构、生产配置和公共契约前取得用户授权。

默认使用下方五步流程，不创建独立迁移报告。出现任一情况时升级为增强验收：

- 跨运行时、跨进程、跨原生/Web 边界，或涉及多个独立构建单元。
- 涉及鉴权、权限、支付、额度、安全、持久化/schema、生产数据或不可逆写入。
- 修改共享公共组件、状态、service/repository/bridge、API 或大量消费者。
- 用户要求严格“一比一”、审计报告、正式验收或可交接的完整证据。
- 用户使用“完整功能、原样迁移、所有功能、保持现有功能、一比一”等完整性表述，即使没有逐字说“一比一”。
- 迁移范围或源行为无法在短时间内界定，存在高影响未知项。

最小分流规则：命中以上任一条件就走增强验收；未命中时走普通五步流程。发现同名覆盖、未授权公共契约变更、数据/安全/权限/生产配置错误或不可逆写入时，先停止写入并将结论标记为 `BLOCKED`。代码级证据已完成但必需运行时或视觉证据尚未完成时，使用 `CODE_ONLY`。

### 严格完整迁移模式

增强验收中的完整性请求必须设置 `parity_mode: STRICT`。严格模式不是“把页面大致做出来”，而是对源入口的可观察功能闭包负责：

1. **源依赖闭包**：从入口递归追踪直接子组件、动态组件、状态/store、请求/API、Bridge/IPC、鉴权、支付/额度、持久化、定时器/observer、埋点、路由和资源；只要会改变用户结果或副作用，就纳入清单。
2. **功能矩阵**：每个源功能必须有目标落点和状态：`PRESERVED`、`ADAPTED`、`MIGRATED` 或 `MISSING`。仅复制标题、卡片或静态布局不能关闭对应功能行。
3. **目标入口激活**：确认目标文件实际映射的 URL、locale 前缀、layout 和入口导航；“代码已写入但用户访问不到”属于未完成。
4. **缺失项阻断**：严格模式下 `MISSING`、未决的数据/权限/支付分支、未激活路由或未经证明的等价替换都计入 `unimplemented_items`；数量大于 0 时结论必须为 `BLOCKED`。
5. **复用等价证明**：目标组件只能在输入、输出、状态、交互、错误和副作用均覆盖源职责时标记 `PRESERVED`；否则只能标记 `ADAPTED` 并记录用户可感知差异。
6. **源渲染契约**：源项目已有可见模板、组件、样式、数据源或交互实现时，它们是 UI 基准。必须把每个可见功能区记录为“源渲染入口 → 目标渲染入口”，并说明模板/DOM、CSS/布局、数据/API、状态、交互、错误和副作用的等价证据。目标同名或相似组件不能自动视为等价；未证明等价时，优先迁入源实现，或标记为 `ADAPTED` 并记录差异，不能标记为 `PRESERVED` 或完成。

严格模式的 `rendering_contract` 至少包含：

- 源渲染入口、源模板/组件和源数据源。
- 目标渲染入口，以及复用、适配或迁入决策。
- DOM/结构、CSS/几何、状态、交互、错误、API 参数/响应和副作用的对照证据。
- 每个用户可见差异及其 `ADAPTED` 或 `MISSING` 状态；没有差异也要写明证据。

严格模式开始写入前必须先完成 C1/C2 及源依赖闭包；闭包不完整、功能矩阵无法逐行落点或目标入口不明确时先停止写入，不得用“目标已有类似组件”代替证据。

增强验收时，在大范围写入前创建精简报告。完整/原样/一比一迁移必须显式使用 `--parity-mode STRICT`：

```bash
python3 scripts/createMigrationReport.py \
  --mode cross-project \
  --platform web-frontend \
  --source <source> \
  --target <target> \
  --reason <升级原因> \
  --parity-mode STRICT \
  --output <report.md>
```

报告默认放在临时目录；只有用户或目标规范要求时才写入产品仓库。

## 标准化流程

### 1. 定范围并追真实链路

读取源、目标生效规范和工作区状态。明确入口、输入、输出、关键状态、错误与副作用，沿实际调用追到状态所有者和 service/repository/bridge/API。严格模式先形成源依赖闭包和功能矩阵；只追踪本次迁移会触达的链路，不为无关分支建立全量资产清单。

### 2. 做目标映射

先搜索目标已有实现，再把源职责按“复用 → 最窄适配 → 最小迁入”映射到目标结构。每个功能矩阵行必须有目标落点、复用/适配理由和消费者影响。每个可见功能区还必须补充源渲染入口、目标渲染入口和等价证据；没有证据时不得用目标近似组件替代源模板。只有修改共享能力时才扫描其直接、间接、动态和自动发现消费者；只有存在文件迁入或路径碰撞风险时才运行：

```bash
python3 scripts/scanMigrationConflicts.py <source-feature-root> <target-root>
```

发现阻断性冲突时先调整映射，不边复制边补救。

### 3. 按纵向切片实现

优先完成一条可运行的主流程，再补关键分支和状态。每个切片同时接好类型/数据、业务逻辑、UI、导航/生命周期、i18n、资源和埋点，避免先复制一层再集中集成。同步更新受影响的导入、导出、注册、路由、tests、targets 和 assets 引用。

### 4. 按风险验证

执行目标项目针对改动范围的 lint、typecheck、测试或构建，并用相同输入验证主流程、关键失败分支、请求/bridge 参数与副作用次数。仅在涉及 UI 时验证对应状态和目标运行时；仅在影响共享能力时回归消费者；仅在导航或生命周期变化时验证进入、离开、刷新/恢复和清理。

严格模式额外检查：源依赖闭包没有孤立节点；功能矩阵不存在 `MISSING`；每个功能区都有 `rendering_contract` 的源/目标渲染映射和证据；路由/locale/layout 已从文件系统或路由表确认；复用项有输入/输出/状态/副作用证据。静态检查、功能运行和视觉运行证据分别报告，不能互相替代。运行环境缺失时明确结论为 `CODE_ONLY`，不要声称已完成运行时验收。

### 5. 交付

日常流程直接总结范围、关键映射、改动、验证结果和残余风险。增强验收补全报告后运行：

```bash
python3 scripts/validateMigrationSpec.py
python3 scripts/validateMigrationReport.py <report.md>
```

退出码 `0` 为 `PASS`，`3` 为结构和代码证据有效但必需运行时/视觉证据待补的 `CODE_ONLY`，`1` 为报告不完整、存在阻断项或验收失败。

## 分层执行

按任务实际涉及的层执行，不适用的层直接跳过，无需制造 `N/A` 清单：

- **契约与逻辑**：保持输入、输出、默认值、校验、状态机、请求参数/次数、错误、取消/重试、缓存、权限、支付、实验和埋点语义。
- **UI 与交互**：使用目标组件、token/theme、i18n、图标和样式系统，覆盖本功能实际存在的初始、加载、空、成功、失败、禁用、hover/focus/pressed、弹层和自适应状态。
- **集成与生命周期**：对齐路由/导航、layout/screen/window、deep link、权限入口、前后台、mount/unmount、订阅/轮询/计时器清理和状态恢复。
- **平台专项**：Web、混合客户端或原生客户端存在平台边界时，读取 [平台执行契约](references/platform-contracts.md) 的对应章节，只执行相关条目。

请求、bridge/IPC、订阅、observer/watcher、轮询、计时器、写入和埋点必须有唯一职责所有者。

## 卡点校验

迁移过程中只保留四个检查点：

- **C1 范围**：真实入口、调用链、可观察结果和允许修改边界已明确。
- **C2 映射**：每项受影响职责有目标落点；无同名覆盖、未授权依赖或未知共享消费者。
- **C3 等价**：主流程、关键分支、数据契约、UI/生命周期适用项和副作用次数符合源基准；严格模式下功能矩阵无 `MISSING`。
- **C4 证据**：相关检查已运行，静态、功能、视觉和未验证项被如实区分，回滚起点明确。

日常流程在工作记录或最终交付中体现结论即可；增强验收才需要把 C1–C4 写入报告。任何数据/安全/权限/生产配置错误、不可逆写入、同名覆盖或未授权公共契约变更都应立即停止写入，解决并复验后继续。

## 验收标准

同时满足以下条件即可完成：

- C1–C4 均成立，没有未解决阻断项。
- 主流程和本次范围内的关键分支行为等价，目标既有受影响消费者无新增回归。
- 严格模式的源依赖闭包、功能矩阵、目标路由激活和 `unimplemented_items=0` 均成立。
- 严格模式的 `rendering_contract` 已逐区记录源/目标渲染入口，并证明模板/DOM、样式/几何、数据、状态、交互、错误和副作用等价；未证明等价的替换不得作为完成项。
- 相关目标项目检查通过；无法运行的检查有原始阻塞原因和残余风险。
- 涉及 UI 时，真实目标运行时覆盖用户可见的关键状态。用户要求精确一比一时，固定数据、设备/视口、scale、主题、语言和字体，保留截图、渲染样式与几何对照；项目或用户给出的误差阈值优先。

结论只使用：`PASS`、`CODE_ONLY` 或 `BLOCKED`。不再用 100 分评分，也不要求对不适用项逐条举证。

增强验收的证据字段、视觉要求和结论规则见 [验收与证据规则](references/migration-contract.md)。

## 故障兜底

遇到失败时回到最早受影响的步骤修复，只重跑受影响检查及其消费者回归。遇到连续返工、冲突不明、重复请求、状态泄漏、平台运行时不可用等情况时，只读取 [高频故障兜底手册](references/failure-playbook.md) 的对应症状，不预加载整套手册。

## 归档规范

日常交付保留：

- 范围与源/目标入口。
- 关键调用链和“复用/适配/迁入”决策。
- 改动文件、消费者影响和用户可感知差异。
- 已运行命令、实际结果、未验证项和残余风险。

增强验收额外保留精简报告、C1–C4 证据、阻断项处理、必需运行时/视觉证据和回滚步骤。报告不得包含密钥、cookie、token、个人数据或生产敏感响应。
